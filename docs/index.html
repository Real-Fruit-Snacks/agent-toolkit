T3 Code and Claude Code on Windows, without admin rights

One GitHub release installs T3 Code, the Claude Code CLI, Node, Git, the GitHub CLI, PowerShell 7 and Python into your own account from a normal PowerShell window, with 36 MCP servers, 240 plugins and every cache they would otherwise download on first run. No UAC prompt, no admin password, and nothing fetched while it runs.

Install, without admin rights

  1. Open PowerShell, not as administrator

    Set-ExecutionPolicy -Scope Process Bypass -Force

    Start it the normal way. Windows PowerShell 5.1, which every Windows 10 and 11 machine has, is enough. Windows blocks downloaded scripts by default; this line lets this one window run them, changes nothing for any other, and needs no admin rights.

  2. Get the scripts

    Clone this repo, or download repo--agent-toolkit-*.zip from the latest release and extract it anywhere you can write to. Run the rest from its root, in the same window.

  3. Download the release

    .\scripts\download-release.ps1

    What a Windows install uses, about 4 GB, into an assets folder there, once it has checked the drive has room. It goes through the GitHub CLI if that's there, and plain HTTPS through your system proxy if not. -Include wsl adds the WSL distro, -All everything.

  4. Check it and restore the folders

    .\scripts\unpack-release.ps1 -From .\assets

    Checks every file against SHA256SUMS.txt, then puts each one back into windows\, linux\, wsl\ or caches\, and this page into page\ to read offline. -Move moves the files instead of copying them, for a small disk.

  5. Install, still without admin rights

    .\scripts\install-windows.ps1

    Puts the apps, the Claude Code CLI and the caches in one folder in your account, adds it to your own PATH, installs the MCP servers, plugins and skills offline, seeds config only where none exists, and sets the user variables that turn off the updaters and telemetry. Open a new terminal afterwards; .\scripts\check-install.ps1 checks it all from there. The download isn't needed after that.

    .\scripts\setup-wsl.ps1

    Imports ubuntu-dev, a distro that already has Git, Node, the GitHub CLI and the Claude Code CLI inside it, into your account. With WSL already on the machine, that needs no admin rights. Turning WSL on in the first place does, once: without WSL the script stops and says so, and from an elevated PowerShell it installs WSL from the bundled MSI, after which Windows may want a reboot.

    sudo bash scripts/install-linux.sh

    For a standalone Debian or Ubuntu machine, where you do need root, with linux/ and caches/ restored: installs T3 Code from the .deb and provisions the same tools as the WSL distro.

Where it all goes

Into your own account and nowhere else, and everything heavy into one folder, the install root: %LOCALAPPDATA%\Programs\agent-toolkit, or wherever -Root puts it. Nothing is installed for other users, so nothing needs an administrator, and taking it out doesn't either.

What the install puts where
WhatWhere
The appsnode, git, gh, pwsh and python in the root: Node.js, the portable Git for Windows, the GitHub CLI, PowerShell 7, and python.org's NuGet build of Python 3.13
Claude Code CLIbin in the root, with the MCP and language-server binaries
MCP servers, pluginsnpm, venv-mcp and plugins in the root: global npm packages, a virtual environment per Python server, the vendored marketplaces
Cachescache in the root: npm's, Playwright's browsers, killer-skills' packs, the Python wheels
T3 Code%LOCALAPPDATA%\Programs\t3code, from its own per-user installer; its data and tool cache in ~\.t3, where T3 keeps them
Skills, config~\.claude and ~\.claude.json, where Claude Code keeps them
PATH and variablesYour user environment, HKCU\Environment, with AGENT_TOOLKIT_HOME pointing at the root. The variables are listed in config/env-vars.md.

To take it out: uninstall T3 Code from Settings, Apps, delete the install root, and remove its entries from your user PATH. Run the install elevated anyway and it warns you, then installs into the elevated account's profile, which is the wrong one if you elevated with someone else's account.

On a VDI desktop

Citrix, VMware Horizon, Azure Virtual Desktop and Windows 365 desktops are the machines this is most often for, and it's built around what they're like.

  • Small disks. The default download is the Windows part only, about 4 GB of the 10, with the free space checked first. unpack-release.ps1 -Move stops the release taking the space twice, and once the install is done you can delete it.
  • Roaming profiles copy everything in the profile except AppData\Local at every logon and logoff. The install root sits in AppData\Local, so the gigabytes stay out of that copy; check-install.ps1 reports what's left in the profile, and every weekly build fails if it passes 1 GB.
  • Desktops reset at logoff keep only the profile. FSLogix profile containers keep all of it, so the default root works. Where AppData\Local isn't kept (classic roaming profiles, some Citrix Profile Management setups), install with -Root on a drive that persists, for example -Root D:\agent-toolkit. check-install.ps1 says which kind of profile it sees.
  • Multi-session hosts are fine: each person installs into their own account, and each T3 Code takes the next free port from 3773.
  • Proxies: download-release.ps1 uses the system proxy with your Windows sign-in, as a browser would. AppData\Roaming on a network share doesn't matter: the install keeps nothing there.
  • WSL 2 needs virtualization that most VDI hosts don't pass through. setup-wsl.ps1 says so when WSL can't start; the Windows install doesn't need it.

Why pin everything

Each of these tools fetches something the first time it runs: an updater, a headless browser, a device agent, a model manifest. On a machine you don't administer, or one that should stay on a known build, those fetches are the problem: some are blocked, and the rest move it off the version you meant. The release carries them all.

The install sets these as user environment variables, among others. The full list, with what each one turns off, is in config/env-vars.md.

T3CODE_DISABLE_AUTO_UPDATE=1
T3CODE_TELEMETRY_ENABLED=0
DISABLE_AUTOUPDATER=1
CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1
npm_config_offline=true
PIP_NO_INDEX=1

The Claude Code provider's endpoint is set per instance in T3 Code, under Settings, Providers, Claude. Templates for an Anthropic-compatible gateway, Bedrock and Vertex are in config/claude-provider-env.example.

How a release is built

By weekly-release.yml, on GitHub's runners. It publishes only after every check below has passed; a failed check stops it before anything is published.

  1. schedule Sundays, 08:00 UTC

    Start

    On its own every week, or by hand from the Actions tab with a pinned T3 tag or Claude Code version, and publishing off to leave a draft for review.

  2. collect Windows runner

    Fetch everything

    collect.ps1 downloads the newest T3 nightly, Claude Code, the Windows apps in the forms that install without admin rights, the plugin marketplaces, the MCP servers and every cache, checks the Node zip and the Python package against their publishers' hashes, and reconciles the versions.

  3. distro Ubuntu runner

    Bake the Linux side

    Builds the Linux wheelhouse natively and the provisioned Ubuntu image in a chroot, then opens the image and checks it: the default MCP servers registered, at least 12 plugins enabled, the skills and binaries in place.

  4. publish Windows runner

    Install as a standard user, pack, verify, publish

    Runs the T3 and Claude Code binaries and check-pins.ps1. Then it makes a new local account with no admin rights and, as that account, in Windows PowerShell 5.1, runs the whole install-windows.ps1, apps included, followed by check-install.ps1, which also fails if more than 1 GB lands where a roaming profile would copy it. Writes VERSIONS.md, packs the assets and cuts any of 1900 MiB or more into parts, uploads a draft, and has verify-release.ps1 compare every digest GitHub recorded with SHA256SUMS.txt. Only then it publishes, rewrites this page, the install log included, and attaches the page to the release as a zip, to read offline.

Tested on

  • A clean GitHub Actions Windows runner, as a standard user: every weekly build installs as a new account with no admin rights, in Windows PowerShell 5.1, and checks the apps, MCP servers, plugins, language servers and skills from that account before it publishes.
  • Windows 11 Pro 26300 with Windows PowerShell 5.1: the bake, collect and pin checks run here.
  • Ubuntu 24.04 noble under WSL 2: the distro is baked and its contents checked here.
  • Not tested: a full install from the release assets on a second physical machine, end to end, or on a managed machine with AppLocker or WDAC rules. Nor on a real VDI desktop yet: the weekly build checks what a plain runner can show (a standard user, the profile footprint), not Citrix, Horizon or FSLogix themselves.

Known issues

  • If Group Policy sets PowerShell's execution policy, Set-ExecutionPolicy -Scope Process can't override it and the scripts won't run. Ask IT to allow them.
  • Where AppLocker, WDAC or another allow-list stops programs from running out of your profile, the per-user apps won't start. Nothing here works around that, on purpose. The scripts also need PowerShell's full language mode, which a WDAC policy can take away.
  • Windows puts the machine PATH before the user PATH, so a Node, Git, GitHub CLI, PowerShell 7 or Python that IT installed for all users runs first in a new terminal. check-install.ps1 says when it does.
  • Turning WSL on needs an administrator, once per machine. Importing the distro after that doesn't. WSL 2 also needs virtualization, which most VDI desktops don't have.
  • On a desktop that doesn't keep AppData\Local between sessions, the default install root is gone at the next sign-in. Install with -Root on a drive that persists.
  • T3 Code's installer runs with silent flags that are right for the pinned build; a newer one may change them.
  • T3 Code pins its on-demand tool versions per build. After bumping T3, run scripts/check-pins.ps1 -Fix, or the cache is ignored and a download is attempted.
  • Importing the raw Ubuntu rootfs instead of the baked distro needs a network to fetch the Playwright browsers.
  • On Linux without PowerShell, join the distro by hand: cat name.part1 name.part2 name.part3 > name, then sha256sum -c name.sha256.
  • The Docker MCP server is Windows-only; its dependencies don't resolve on Ubuntu's Python 3.12.
